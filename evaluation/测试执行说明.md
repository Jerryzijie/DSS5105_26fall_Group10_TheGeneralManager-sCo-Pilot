# 怎么测

每人自己测一轮。每人提问量预算（可60题左右，根据问题复杂度浮动）

## 开始之前

先确认程序能正常打开，使用ai或自行检查当前的版本是否存在死循环等异常情况。

确认使用的api key正确，使用的模型名字为**gpt-5.6**。

## 提问之前

检查自己将要发送的问题，注意不要出现错别字或输入错误导致问题无效的情况。

## 问完之后

**记下每一题。** 每一题记下：问题原文、完整回答。如果出现选择按钮，上面的句子也要抄下来。

根据你的判断，将回答进行分类，分为good和bad两个文件进行存储。（可保存成json等任意形式，只要信息完整即可）

**如果回答存在严重的bug，请及时在群里@我或私信提出**

**全部问完选择。**

- 最让你惊喜的三题：感觉wow的，或者对于回答比较满意的。
- 最让你失望的三题：回答存在错误/不能回答等任何问题的。

写一个简短的说明，为什么选择这道题（不需要很长，简述即可，如：问题回答思路清晰/回答没有很好贴合问题等）

不够三题就写实际有的，不要硬凑。

**对以下两个问题进行打分，10分为满分，1分为最低分，可打小数分**

- OVERALL Satisfaction：对于模型的整体使用体验，进行打分。
- Waiting Time Satisfaction：对于模型回复的中间回复生成等待时间，整体满意度打分。

**所有内容保存在jira上即可**

**使用注意点：**

1. 当前的模型具有**追问**功能：追问指模型会根据上一轮的回复来进行后续的回复。
eg. “请查看TrendCart的Orders数据"→“List all the risk orders" 此时模型的回复会基于第一轮回答的trendcart筛选条件而不是基于全部订单。如果要清楚上下文，请刷新页面重置

2. 当前的模型具有**澄清**功能：当模型认为你的提问具有多种回答的方式时，会生成澄清，澄清会弹出多个可能的回答方式供你选择，也可以在others中输入你想要的回答方式，澄清触发后模型会根据澄清的结果来进行回答。

3. **拦截**：模型会判断当前的问题是否数据支持、工具支持，如果都不支持的情况下就会直接被拦截不给回复，此处的拦截目前还有待优化（若限制太松会导致无效限制，因此限制相对比较严），可能会存在一些边界问题可以回答但被错判为不能回答的情况，可以记录后续反馈优化。

3. **语言**：当前版本修复了模型乱跳法语、西语的问题，但将模型的语言能力限制在了仅支持中文和英文上（这是目前的boundary），其他语言暂时不支持。

4. **图表**：当前模型的回复都会主动调用图表来优化回答可读性，但由于ReAct结构问题，小概率会出现：
    a. 模型调用绘图工具错误返回error并显示在回复中
    b. 模型调用绘图工具后错误以为工具结果要输出在回复中导致回复信息时间极长且内容冗长（此问题已经修复但不确定是否测试还会发生，若发生需要及时反馈给我，因为会导致烧掉大量token的情况）

## 逻辑架构

1. 问题先通过 `assess_ambiguity`。存在两种及以上的合法 answer method 时，先出 clarification card，不查数。点击后以 `clarification_reply` 进入后续流程，模型按所选澄清继续后续回复。

2. 问题已经无歧义后，再过双层门，两层都通过才进入 ReAct agent：

a. Stored-data gate（`assess_stored_data`）：该 fact 是否在表里。不在则拦截，`limitation=missing_data`。销售、售价、revenue 不在库中。
b. Tool-coverage gate（`assess_tool_coverage`）：现有 tool 能否取出该 fact。在库中但没有对应 tool 则拦截，`limitation=no_tool`。

3. 通过后 agent 调用业务 tool。当Retrieval 返回数据后，**必须**再调用 `draw` 或 `render_table` 之一；图和表只展示，不参与计算。

4. Tool 返回 `AMBIGUOUS`（多行匹配、不能代选）时，会再出 clarification card回到澄清步骤。

## 功能点

- 单笔订单状态：`get_order_status`
- 按 customer、product、stage、status 列订单：`find_orders`
- 默认 at-risk 名单：`get_orders_at_risk`。不传 flag 时等于 `likely_to_miss_due_dates`：未逾期、due 在今天至 +3 个日历日、且 `days_left` 大于剩余工作日。`flag=OVERDUE` 与 `flag=STALLED` 单独查询，不进入默认名单
- 今日优先级 1st / 2nd / 3rd：`get_today_priority`
- 早报：`get_morning_briefing`
- 订单轨迹与风险依据：`trace_order`
- 产量异常：`discover_factory_issues`
- 新订单可行性：`check_feasibility`
- 催货草稿、发送、备注、提醒：`draft_chase_email`、`send_email`、`add_order_note`、`create_reminder`
- 持续观察：`create_watch`、`list_watches`、`cancel_watch`
- 近期已确认操作：`get_recent_actions`
- 展示：`draw`、`render_table`

`days_left` = 剩余各 stage 的件数 / 该 stage 近 30 个工作日平均日产量。`discover_factory_issues` 的产量对比，以及 `check_feasibility` 的 bottleneck，仍用 30 日 median。`production_log` 是全厂 date × stage 产量，不是单笔订单产量。
